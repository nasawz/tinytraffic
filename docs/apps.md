# App analytics

tinytraffic can count the users of mobile and desktop apps, not only web
visitors. An app is a **site**: add one in the dashboard and use the app's ID
(e.g. its bundle ID, `com.example.app`) as the domain.

Apps differ from websites in one way that matters: they know who they are.
Each install sends a random device ID, so the same user is the same visitor
on every day. That makes these possible, and they show up on the site's
dashboard as soon as the first app event arrives:

- **Daily, weekly and monthly active users** (rolling 1, 7 and 30 days up to
  the end of the selected period)
- **New and returning users**
- **Retention**: of the users first seen on a day, how many were active again
  1, 2, 3, 7, 14 and 30 days later
- **Breakdowns** by app version, build, OS version, device model, language,
  country, channel and screen. Click a row to filter everything else by it.

Pageviews, visits, bounce rate and visit duration work as on the web: a
screen view is a pageview and a session is a visit.

## Privacy

- The device ID is generated by the app, is not an advertising or hardware ID,
  and is deleted with the app. Reinstalling counts as a new install.
- The server hashes it with the site ID before storing it, so the same device
  is a different visitor in each app.
- The IP address is used for the country and city, then discarded.
- Nothing is sent before you call the SDK. Start with `enabled: false` and
  switch on later (`TinyTraffic.setEnabled(true)` / `isEnabled = true`) to wait
  for the user's consent. Switching off stops collection and discards events
  that were not sent yet.

## SDKs

| Platform | Where | Install |
|---|---|---|
| iOS / macOS (Swift) | [`sdk/ios`](../sdk/ios) | Swift Package: add the folder or the repo URL |
| HarmonyOS (ArkTS) | [`sdk/ohos`](../sdk/ohos) | copy `TinyTraffic.ets` into the app |

Both do the same: start a session at launch (new one after 30 minutes in the
background), record `app_open`, queue events, send them in batches, and keep
what could not be sent for the next launch.

### iOS

```swift
import TinyTraffic

// App launch
TinyTraffic.shared.configure(endpoint: "https://stats.example.com",
                             appId: "com.example.app",
                             channel: "appstore",
                             debug: isDebugBuild)

// SwiftUI: a screen view each time the view appears
ClosetView().trackScreen("closet")

// Anything else
TinyTraffic.shared.track("outfit_saved", props: ["items": 4])
```

### HarmonyOS

```ts
import { TinyTraffic } from './TinyTraffic';

// EntryAbility.onCreate
TinyTraffic.init(this.context, { endpoint: 'https://stats.example.com', appId: 'com.example.app', channel: 'appgallery' });

TinyTraffic.screen('closet');
TinyTraffic.track('outfit_saved', { 'items': 4 });
```

The app needs the `ohos.permission.INTERNET` permission. ArkTS wants quoted
keys in prop objects (`{ 'items': 4 }`).

### Conventions

- `screen("closet")` records a pageview of `/closet`. Use stable names, not
  titles that change with the language.
- Events other than `screen_view` are custom events and show up under Goals.
  Props are flat string pairs; at most 30 per event.
- Don't put personal data (names, phone numbers, photos) in names or props.
- `debug: true` records and sends nothing, so development builds don't count.

## Sending events yourself

`POST /api/app/event` needs no key, like the web endpoint. It always answers
`202` once the payload is valid, and never reveals whether the app ID exists.

```sh
curl -X POST https://stats.example.com/api/app/event -d '{
  "app_id": "com.example.app",
  "device_id": "5b0c1a6e-…",
  "session_id": "d41f…",
  "os": "iOS", "os_version": "26.1",
  "app_version": "1.6.0", "build": "13",
  "device_model": "iPhone17,1", "device_type": "phone",
  "locale": "zh-Hans-CN", "screen_width": 393,
  "channel": "appstore",
  "events": [
    {"name": "screen_view", "screen": "closet", "ts": 1731200000000},
    {"name": "outfit_saved", "screen": "studio", "props": {"items": 4}}
  ]
}'
```

| Field | |
|---|---|
| `app_id`, `device_id` | Required. The site's domain and the install's random ID. |
| `session_id` | Any string, one per app session. Without it, 30 minutes without events end a session. |
| `os`, `os_version`, `app_version`, `build`, `device_model`, `locale` | Shown in the breakdowns. |
| `device_type` | `phone`, `tablet` or `desktop`. |
| `screen_width` | In points; used when `device_type` is missing. |
| `channel` | Distribution channel, shown under Sources. |
| `debug` | `true` drops the request. |
| `events[].name` | `screen_view` (or `pageview`) for screens, anything else for custom events. |
| `events[].ts` | Epoch milliseconds. Offline events keep their time if it's within the last 7 days; otherwise the server's time is used. |

At most 100 events and 128 KB per request.

## Reading the stats

The dashboard's API also has two app endpoints, besides the usual
`aggregate`, `timeseries` and `breakdown` (which take `app_version`,
`app_build`, `device_model` and `locale` as dimensions and filters):

- `GET /api/sites/{site}/app?period=30d` returns `dau`, `wau`, `mau`,
  `new_users`, `returning_users`, `total_users` and `is_app`.
- `GET /api/sites/{site}/retention?days=14` returns one cohort per day, each
  with `size` and `retained[0..30]` (`null` for days that haven't happened).
